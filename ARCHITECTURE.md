# LuxFatum裁定對決 Core Architecture

This document defines the current architecture boundaries for the MVP/demo. It records how the existing project is organized; it is not a request to rewrite the application.

## Runtime Shape

The browser app starts at:

```text
index.html -> src/main.tsx -> src/App.tsx
```

The production web build is generated by Vite:

```text
npm run build -> web-build/
```

The deployable Node server starts at:

```text
npm start -> server.js
```

## Source Boundaries

### Frontend Shell

- `index.html` owns the HTML mount point and static metadata.
- `src/main.tsx` mounts React and imports global styles.
- `src/App.tsx` owns the main application composition, game screen state, menu flow, and UI wiring.
- `src/styles.css` owns global visual styling for the current app.

Do not move gameplay rules into `src/main.tsx` or `index.html`.

### Game Domain

- `src/types.ts` is the shared TypeScript contract for game state, fighters, cards, actions, screens, and rules data.
- `src/game.ts` owns core battle rules, rule constants, turn flow helpers, and the current browser rules bridge.
- `src/data/characters.ts` owns character/card definitions.
- `src/data/rulesGuide.ts` owns player-facing rules guide content.
- `src/progression.ts` owns progression-related helpers.
- `src/settings.ts` owns configurable client settings.

Gameplay behavior changes should be paired with focused rule checks in `scripts/test-rules.mjs`.

### Components And Rendering

- `src/components/OpeningTrailer.tsx` owns opening/trailer presentation.
- `src/components/PixiBattle.tsx` owns Pixi-based battle presentation.
- `src/rendering/` is reserved for rendering-specific code when needed.

Components may call domain helpers through the app layer, but rendering code should not become the source of truth for game rules.

### Network Layer

- `src/network/messages.ts` owns network message contracts.
- `src/network/NetworkTransport.ts` defines the transport boundary.
- `src/network/LocalMockTransport.ts` supports local/mock transport behavior.
- `src/network/LobbyManager.ts` owns lobby coordination helpers.
- `src/network/HostGameSession.ts` and `src/network/ClientGameSession.ts` own host/client session behavior.
- `src/network/SteamBridgeTransport.ts` and `src/network/SteamPrivateLobby.ts` own Steam-specific transport/lobby behavior.
- `src/network/stateHash.ts` owns deterministic state hash helpers.
- `src/network/index.ts` is the public export barrel for network modules.

Network code may depend on shared game types. Core game rules should not depend on network transports.

### Server

`server.js` is a dependency-light Node HTTP server, not an Express app.

Current public routes:

- `GET /api/version`
- `GET /api/health`
- `POST /api/create`
- `POST /api/join`
- `GET /api/state`
- `POST /api/state`
- `GET /download/package.zip`
- `GET /download/windows.zip`
- `GET /download/installer.exe`

Server room state is in-memory. Do not treat it as durable persistence.

Any public API route or payload change must be documented in `progress.txt` and should include an explicit compatibility note.

### Assets

- `public/assets/` is the source location for browser-served static assets.
- `public/assets/portraits/` contains character portrait assets.
- `public/assets/audio/` contains audio assets.
- `public/assets/images/` contains image backgrounds and scene assets.
- `public/assets/ui/` contains app icons and UI branding.

Do not hand-edit generated copies of assets under build or package output folders.

### Build And Generated Output

Generated outputs:

- `web-build/` from `npm run build`
- `artifacts/` from smoke/UI checks and other generated evidence
- `dist/`, `output/`, and installer files from packaging/release flows
- `test-results/` from test tooling

Generated outputs are not the source of truth. Fix source files first, then regenerate outputs.

### Packaging Surfaces

- `render.yaml` and `Dockerfile` support Render/container deployment.
- `electron/` supports desktop/Steam adapter integration.
- `launcher/` and `installer/` support Windows packaging.
- `scripts/package-release.mjs` supports release bundle generation.
- `scripts/audit-steam-readiness.mjs` supports Steam/release readiness checks.

Packaging changes belong to deployment/package steps unless a current task explicitly requires them.

## Architecture Locks

- Keep the current tech stack: Vite, React, TypeScript, Node.js, npm.
- Keep `server.js` dependency-light unless a future step explicitly approves server framework changes.
- Keep public API route changes documented.
- Keep game rules centralized in `src/game.ts` and shared contracts in `src/types.ts`.
- Keep `src/network/` transport-specific behavior out of core game rules.
- Treat `web-build/`, `artifacts/`, `dist/`, `output/`, and `test-results/` as generated output.
- Do not add unrelated dependencies to solve architecture problems.
- Do not refactor large files only for style during MVP steps.

## Current Architecture Risks

- `src/App.tsx`, `src/game.ts`, and `src/styles.css` are large files. Future work should change them surgically unless an active step specifically authorizes refactoring.
- `server.js` combines static serving, downloads, API proxying, and in-memory room state. Keep route changes narrow until the architecture review gate approves larger changes.
- Some generated and release artifacts are present in the repository. Future packaging/deployment steps should decide what remains tracked.
